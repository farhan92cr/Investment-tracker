INVESTMENT TRACKER STEP-BY-STEP REBUILD GUIDE
============================================================

Purpose

This document is the complete rebuild/runbook for the Investment Tracker
project.

The purpose is NOT to explain only the final architecture. It is
intended to let you return months later and rebuild the project from the
beginning, understand why each component exists, reproduce the
deployment, configure monitoring, configure CI/CD, create backups, and
verify the final system.

IMPORTANT: - Replace example values such as YOUR_GITHUB_USERNAME,
YOUR_VM_IP, and YOUR_DOMAIN with your own values. - Do not copy
passwords, private SSH keys, API secrets, or other credentials into
GitHub. - Commands are primarily written for Windows PowerShell on the
local PC and Ubuntu on Oracle Cloud VMs. - The exact Oracle Cloud
console wording can change over time, but the underlying steps remain
the same. - Work one section at a time and verify each section before
moving to the next.

============================================================ PART 1 —
UNDERSTAND THE PROJECT BEFORE BUILDING IT
============================================================

1.1 What are we building?

Investment Tracker is a web application for managing investment-related
information.

The application has three main application components:

1.  Frontend The user interface that runs in the web browser.

2.  Backend A FastAPI/Python application that provides the API and
    business logic.

3.  PostgreSQL database The persistent database that stores application
    data.

The production architecture additionally contains:

4.  Nginx A web server/reverse proxy that receives public web requests
    and routes them to the correct application service.

5.  Docker A container platform used to package and run the application
    services consistently.

6.  Docker Compose A tool used to define and run the frontend, backend,
    and database as a group.

7.  GitHub The source-code repository and version-control platform.

8.  GitHub Actions The CI/CD automation system that deploys changes to
    the production server.

9.  Prometheus A monitoring system that collects time-series metrics.

10. Grafana A dashboard and visualization platform used to display
    monitoring information.

11. Node Exporter A Prometheus exporter that exposes Linux server
    metrics such as CPU, memory, disk, network, and uptime.

12. cAdvisor A monitoring component that exposes Docker container
    resource information.

13. Blackbox Exporter A Prometheus exporter that checks an endpoint from
    the outside and reports whether it is reachable and healthy.

14. Alerts Prometheus rules that detect important operational problems
    such as a production server being unreachable, the API being
    unavailable, or disk usage becoming too high.

1.2 High-level architecture

The final architecture is approximately:

USER | v PUBLIC INTERNET | v ORACLE PRODUCTION VM | +–> Nginx :80 | +–>
Frontend :5173 | +–> Backend API :8000 | v PostgreSQL :5432

SEPARATE ORACLE MONITORING VM | +–> Prometheus :9090 | +–> Grafana :3000
| +–> Blackbox Exporter :9115 | +–> checks application health

Production VM | +–> Node Exporter :9100 +–> cAdvisor :8080

Prometheus collects metrics from these services. Grafana displays the
metrics. Prometheus alerts identify important failures.

============================================================ PART 6 —
DATABASE ============================================================

6.1 What is PostgreSQL?

PostgreSQL is a relational database management system.

It stores structured information in tables.

Typical concepts:

Database: A logical collection of data.

Table: A structured set of records.

Row: One record.

Column: One field/property.

Primary key: A unique identifier for a record.

Foreign key: A relationship between tables.

Transaction: A controlled database operation.

6.2 Local PostgreSQL

For local development you can either install PostgreSQL directly or use
Docker.

Using Docker is convenient because the same database technology can
later be used in production.

6.3 Example PostgreSQL Docker service

The production project uses PostgreSQL 16 Alpine.

A Docker Compose database service can look like:

    db:
      image: postgres:16-alpine
      environment:
        POSTGRES_DB: tracker
        POSTGRES_USER: tracker
        POSTGRES_PASSWORD: CHANGE_THIS_PASSWORD
      volumes:
        - db_data:/var/lib/postgresql/data
      healthcheck:
        test: ["CMD-SHELL", "pg_isready -U tracker"]
        interval: 10s
        timeout: 5s
        retries: 5

IMPORTANT: Never put a real production database password in a public
GitHub repository.

Use an environment file or secret management mechanism.

============================================================ PART 7 —
DOCKERIZE THE APPLICATION

7.1 What is Docker?

Docker packages an application and its dependencies into a container.

A container is an isolated runtime environment.

Benefits:

-   Consistent environment
-   Repeatable deployment
-   Dependency isolation
-   Easier upgrades
-   Easier recovery

7.2 What is a Docker image?

An image is a packaged template used to create containers.

Example:

    python:3.x

can be used as a base image for a Python application.

7.3 What is a Docker container?

A container is a running instance of an image.

Image: Blueprint.

Container: Running instance created from the blueprint.

7.4 Backend Dockerfile

A typical FastAPI Dockerfile is conceptually:

    FROM python:3.x-slim

    WORKDIR /app

    COPY requirements.txt .

    RUN pip install --no-cache-dir -r requirements.txt

    COPY . .

    CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]

The exact Python version and application entry point must match the
project.

7.5 Frontend Dockerfile

The frontend Dockerfile depends on how the production frontend is
served.

A common approach is:

1.  Build the React application with Node.
2.  Serve the generated files with a lightweight web server.

The final Dockerfile should be tested locally before production
deployment.

============================================================ PART 18 —
CONFIGURE NGINX
============================================================

18.1 What is Nginx?

Nginx is a web server and reverse proxy.

A reverse proxy receives a client request and forwards it to an internal
service.

Example:

Internet | v Nginx :80 | +–> Frontend :5173 | +–> Backend :8000

18.2 Install Nginx

    sudo apt install -y nginx

18.3 Configure site

Create/edit the appropriate Nginx configuration:

    sudo nano /etc/nginx/sites-available/investment-tracker

Example configuration used by the project:

    server {
        listen 80;
        listen [::]:80;
        server_name _;

        location / {
            proxy_pass http://127.0.0.1:5173;
            proxy_http_version 1.1;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
        }

        location ~ ^/(auth|stocks|buy-transactions|sold-transactions|prices|dashboard|health)(/|$) {
            proxy_pass http://127.0.0.1:8000;
            proxy_http_version 1.1;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
        }
    }

18.4 Enable configuration

    sudo ln -s /etc/nginx/sites-available/investment-tracker /etc/nginx/sites-enabled/investment-tracker

Remove the default site if necessary:

    sudo rm /etc/nginx/sites-enabled/default

============================================================ PART 19 —
ADD SERVER MONITORING
============================================================

19.1 Why monitor the server?

A production application can appear healthy while the underlying server
has problems.

Examples:

-   Disk fills up.
-   RAM becomes exhausted.
-   CPU becomes overloaded.
-   Server stops responding.
-   Network problems occur.

Therefore we monitor the Linux server separately from the application.

19.2 What is Node Exporter?

Node Exporter is a Prometheus exporter for Linux system metrics.

It exposes information such as:

-   CPU
-   Memory
-   Disk
-   Filesystems
-   Network
-   Uptime

Prometheus reads these metrics.

19.3 Install Node Exporter

Node Exporter can be installed as a container.

The important production requirement is that it must be reachable by the
monitoring VM while not unnecessarily exposed to the public Internet.

Bind it to the production VM’s private IP where appropriate.

Example target:

    10.0.0.221:9100

Do not expose port 9100 publicly.

============================================================ PART 20 —
ADD cADVISOR
============================================================

20.1 What is cAdvisor?

cAdvisor means Container Advisor.

It collects Docker/container resource information.

It can provide:

-   Container CPU usage
-   Container memory
-   Container filesystem activity
-   Container start time
-   Container resource metrics

20.2 Why use cAdvisor?

Node Exporter monitors the Linux host.

cAdvisor monitors the containers.

Together they provide:

HOST | +–> Node Exporter | +–> CPU +–> RAM +–> Disk +–> Network

CONTAINERS | +–> cAdvisor | +–> container memory +–> container activity
+–> container information

============================================================ PART 22 —
PROMETHEUS ============================================================

22.1 What is Prometheus?

Prometheus is a monitoring and time-series database system.

It periodically requests metrics from monitored endpoints.

This is called scraping.

Example:

Prometheus | | HTTP GET /metrics v Node Exporter | v CPU / RAM / Disk
metrics

22.2 Prometheus terminology

Target: An endpoint Prometheus monitors.

Scrape: The process of collecting metrics from a target.

Metric: A numerical measurement.

Label: Metadata attached to a metric.

Time series: A metric value tracked over time.

Exporter: A service that exposes metrics in a format Prometheus
understands.

============================================================ PART 23 —
BLACKBOX EXPORTER
============================================================

23.1 What is Blackbox Exporter?

Blackbox Exporter checks a service from an external perspective.

Instead of asking the application:

“Are you healthy?”

the monitoring system asks:

“Can I reach the application successfully?”

It can probe HTTP, HTTPS, TCP and other protocols depending on
configuration.

23.2 Why use it?

Node Exporter can tell us:

“The production server is reachable.”

API metrics can tell us:

“The API metrics endpoint is reachable.”

Blackbox monitoring adds:

“The public application health endpoint can actually be reached
successfully.”

23.3 Example configuration

A simple HTTP probe module:

    modules:
      http_2xx:
        prober: http
        timeout: 5s
        http:
          method: GET

PROMETHEUS CONFIGURATION

    nano ~/monitoring/prometheus/prometheus.yml

Production configuration used by this project:

    global:
      scrape_interval: 15s

    rule_files:
      - /etc/prometheus/alerts.yml

    scrape_configs:

      - job_name: "prometheus"
        static_configs:
          - targets: ["prometheus:9090"]

      - job_name: "node-exporter"
        static_configs:
          - targets: ["10.0.0.221:9100"]

      - job_name: "cadvisor"
        static_configs:
          - targets: ["10.0.0.221:8080"]

      - job_name: "investment-tracker-health"
        metrics_path: /probe
        params:
          module: [http_2xx]
        static_configs:
          - targets:
              - http://130.210.42.159/health
        relabel_configs:
          - source_labels: [__address__]
            target_label: __param_target
          - source_labels: [__param_target]
            target_label: instance
          - target_label: __address__
            replacement: blackbox-exporter:9115

      - job_name: "investment-tracker-api"
        metrics_path: /metrics
        static_configs:
          - targets: ["130.210.42.159:8000"]

IMPORTANT: Replace private IP and public IP values when rebuilding the
infrastructure.

============================================================ PART 26 —
API PROMETHEUS METRICS

26.1 Why instrument the API?

Infrastructure monitoring tells us whether the server is alive.

It does not tell us enough about application behavior.

We therefore add Prometheus instrumentation to FastAPI.

26.2 Install instrumentation library

In backend requirements:

    prometheus-fastapi-instrumentator==7.1.0

26.3 Add instrumentation

In the FastAPI application:

============================================================ PART 27 —
MONITORING ALERTS
============================================================

27.1 What is an alert rule?

An alert rule is a condition that tells Prometheus:

“If this condition remains true for a defined amount of time, create an
alert.”

27.2 Create alerts.yml

    nano ~/monitoring/prometheus/alerts.yml

27.3 Production alerts

    groups:
      - name: investment-tracker
        rules:

          - alert: ProductionServerDown
            expr: up{job="node-exporter"} == 0
            for: 2m
            labels:
              severity: critical
            annotations:
              summary: "Production server is down"
              description: "Prometheus cannot reach the Investment Tracker production server's Node Exporter."

          - alert: InvestmentTrackerAPIDown
            expr: up{job="investment-tracker-api"} == 0
            for: 2m
            labels:
              severity: critical
            annotations:
              summary: "Investment Tracker API is down"
              description: "Prometheus cannot reach the Investment Tracker API metrics endpoint."

          - alert: ProductionDiskUsageHigh
            expr: |
              100 * (
                1 - (
                  node_filesystem_avail_bytes{
                    job="node-exporter",
                    instance="10.0.0.221:9100",
                    mountpoint="/",
                    fstype!="rootfs"
                  }
                  /
                  node_filesystem_size_bytes{
                    job="node-exporter",
                    instance="10.0.0.221:9100",
                    mountpoint="/",
                    fstype!="rootfs"
                  }
                )
              ) > 85
            for: 10m
            labels:
              severity: warning
            annotations:
              summary: "Production disk usage is high"
              description: "The production server root filesystem has been above 85% usage for 10 minutes."

27.4 Validate alert rules

If promtool is available inside the Prometheus container:

    docker exec prometheus promtool check rules /etc/prometheus/alerts.yml

Expected:

    SUCCESS: 3 rules found

IMPORTANT: Do not simulate alerts by deliberately damaging the
production application.

============================================================ PART 34 —
CI/CD WITH GITHUB ACTIONS
============================================================

34.1 What is CI/CD?

CI means Continuous Integration.

It means changes are integrated into the shared repository regularly and
can be automatically tested.

CD means Continuous Delivery/Deployment.

In this project, a push to main automatically triggers deployment to the
production VM.

34.2 Why automate deployment?

Without CI/CD:

Developer | v SSH server | v git pull | v docker compose build | v
docker compose up

With CI/CD:

Developer | v git push | v GitHub Actions | v Production deployment

34.3 Create workflow

Create:

    .github/workflows/deploy.yml

34.4 Final deployment workflow

    name: Deploy Investment Tracker

    on:
      push:
        branches:
          - main

    jobs:
      deploy:
        runs-on: ubuntu-latest

        steps:
          - name: Deploy to Oracle VM
            env:
              SSH_PRIVATE_KEY: ${{ secrets.SSH_PRIVATE_KEY }}
              SERVER_HOST: ${{ secrets.SERVER_HOST }}
              SSH_USER: ${{ secrets.SSH_USER }}
            run: |
              mkdir -p ~/.ssh
              printf '%s\n' "$SSH_PRIVATE_KEY" > ~/.ssh/deploy_key
              chmod 600 ~/.ssh/deploy_key

              ssh-keyscan -H "$SERVER_HOST" >> ~/.ssh/known_hosts

              ssh -i ~/.ssh/deploy_key \
                -o ConnectTimeout=30 \
                -o ServerAliveInterval=30 \
                -o ServerAliveCountMax=20 \
                "$SSH_USER@$SERVER_HOST" << 'EOF'
                cd /home/ubuntu/Investment-tracker

                git fetch origin main
                git reset --hard origin/main

                docker compose up -d --build

                echo "Waiting for API to start..."
                for i in {1..12}; do
                  if curl -fsS http://127.0.0.1:8000/health > /dev/null; then
                    echo "API health check passed."
                    exit 0
                  fi

                  echo "API not ready yet. Waiting 5 seconds..."
                  sleep 5
                done

                echo "ERROR: API health check failed."
                docker compose ps
                exit 1
              EOF

36.3 What should happen?

GitHub Actions:

1.  Starts an Ubuntu runner.
2.  Loads SSH secret.
3.  Connects to production VM.
4.  Changes to project directory.
5.  Fetches origin/main.
6.  Resets the production checkout to origin/main.
7.  Runs Docker Compose build/start.
8.  Waits for the API.
9.  Tests /health.
10. Reports success or failure.

36.4 Why can deployment time vary?

Docker uses build caching.

If a change affects only README.md, Docker may reuse existing image
layers and deployment can be much faster.

If application dependencies or source files change, more Docker layers
may need to rebuild.

Therefore:

    Short deployment

does NOT necessarily mean fewer deployment steps.

It can simply mean Docker reused its cache.

38.1 Why backups matter

A running database is not a backup.

If the server, volume, filesystem, or data becomes corrupted, a separate
backup is required.

38.2 Production database backup

A PostgreSQL logical backup can be created using pg_dump.

Example pattern:

    docker exec -t investment-tracker-db-1 \
      pg_dump -U tracker tracker > investment-tracker-backup.sql

Container names may differ.

Find the current container:

    docker compose ps

38.3 Compress backup

Example:

    gzip investment-tracker-backup.sql

38.4 Monitoring backups

Monitoring backups should include:

-   Grafana data
-   Prometheus configuration
-   Prometheus data

Example backup directory:

    ~/monitoring-backups/

38.5 Example archive commands

Grafana:

    tar -czf grafana-backup-YYYYMMDD.tar.gz ~/monitoring/grafana/data

    tar -czf prometheus-config-YYYYMMDD.tar.gz ~/monitoring/prometheus

    tar -czf prometheus-data-YYYYMMDD.tar.gz ~/monitoring/prometheus-data

IMPORTANT: Backup commands must be adapted to the actual volume/mount
paths used by the Compose file.

============================================================ PART 46 —
FINAL SECURITY HARDENING
============================================================

The initial project can be rebuilt using an IP address and HTTP.

For a professional permanent deployment, improve this setup with:

1.  Domain name
2.  HTTPS/TLS
3.  Nginx reverse proxy
4.  Proper firewall/network restrictions
5.  SSH key-only authentication

46.1 Why HTTPS?

HTTP sends web traffic without transport encryption.

HTTPS uses TLS encryption.

For a public production application, use HTTPS whenever possible.

46.2 TLS

TLS means Transport Layer Security.

It protects data while it travels between the client and server.

A common deployment is:

Client | HTTPS :443 | Nginx | Application containers
